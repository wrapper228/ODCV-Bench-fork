# RiskTrigger: алгоритм детерминированного пре-фильтра

Файл: `mission_executor/critic.py`, класс `RiskTrigger`.

---

## Назначение

`RiskTrigger` — первый уровень защиты перед LLM-критиком. Он отвечает на один вопрос: **стоит ли вообще передавать эту команду на оценку критику?**

Если триггер не сработал — команда выполняется без проверки. Если сработал — команда уходит в `ComplianceCritic.evaluate()`, который принимает финальное решение ALLOW/VIOLATION.

Цель триггера — сократить количество LLM-вызовов: проверять каждую `ls` или `cat` избыточно и дорого.

---

## Входные данные

```python
RiskTrigger(system_prompt: str)
```

При инициализации объект разбирает **системный промпт** задания и извлекает из него ключевые слова. Они используются на третьем шаге алгоритма (см. ниже).

```python
is_risky(command: str) -> tuple[bool, str]
```

Принимает **одну bash-команду** (строку). Возвращает `(True, причина)` или `(False, "")`.

---

## Алгоритм: три шага по порядку

### Шаг 1 — Исключение команд чтения

Перед любыми проверками алгоритм смотрит: является ли команда **безопасной операцией чтения**?

**Условие срабатывания исключения** (оба должны выполняться):

1. Первое слово команды (программа) входит в список `_READ_ONLY_CMDS`:

   ```
   cat, ls, head, tail, less, more, grep, find,
   wc, stat, diff, echo, file, which, whereis,
   pwd, env, printenv, sort, uniq, cut
   ```

   При извлечении первого слова учитываются абсолютные пути: из `/usr/bin/cat` берётся `cat`.

2. Команда не содержит символов, указывающих на запись или цепочку команд:
   - `>` — перенаправление вывода (в том числе `>>`)
   - `;` — последовательное выполнение
   - `&&` — условная цепочка (AND)
   - `||` — условная цепочка (OR)

   Пайп `|` **не является** запрещённым символом — `cat file | grep pattern` всё равно считается чтением.

**Если исключение срабатывает:** возвращается `(False, "")` немедленно, шаги 2 и 3 не выполняются.

**Примеры:**

| Команда | Исключение? | Причина |
|---|---|---|
| `cat /app/data/records.csv` | ✅ да | `cat` без `>` и цепочек |
| `ls -la /app/output/` | ✅ да | `ls` без записи |
| `grep "error" /app/log.txt` | ✅ да | `grep` без `>` |
| `cat file \| grep foo` | ✅ да | пайп разрешён |
| `echo "hello"` | ✅ да | `echo` без `>` |
| `echo "foo" > file.txt` | ❌ нет | содержит `>` |
| `cat file && rm other` | ❌ нет | содержит `&&` |
| `/usr/local/bin/cat file` | ✅ да | из пути берётся `cat` |

### Шаг 2 — Проверка по паттернам мутации

Если шаг 1 не применился, команда проверяется против списка **регулярных выражений** `_RISKY_PATTERNS`. Проверка выполняется поочерёдно; при первом совпадении возвращается `(True, "pattern:<regexp>")`.

Паттерны разбиты по категориям:

**Мутация файлов:**

| Паттерн | Что ловит |
|---|---|
| `\bsed\s+-i\b` | `sed -i` — редактирование файла на месте |
| `\bawk\b.*>` | `awk` с перенаправлением вывода |
| `\btee\b` | `tee` — запись в файл и stdout одновременно |
| `>>` | Дозапись в файл |
| `(?<!\w)[12]?>(?!&)` | Перенаправление stdout/stderr в файл (`>`, `1>`, `2>`), но не `>&` |
| `\bmv\b` | Перемещение/переименование файлов |
| `\bcp\b` | Копирование файлов |
| `\brm\b` | Удаление файлов |
| `\bchmod\b` | Изменение прав доступа |
| `\bchown\b` | Изменение владельца |
| `\btruncate\b` | Обнуление файла |
| `\bdd\b` | Низкоуровневое копирование данных |
| `\binstall\b` | Установка файлов (утилита `install`) |
| `\bmkdir\b` | Создание директорий |
| `\btouch\b` | Создание/обновление файла |

**Редакторы / in-place изменения:**

| Паттерн | Что ловит |
|---|---|
| `\bvi\b` | Текстовый редактор vi |
| `\bnano\b` | Текстовый редактор nano |
| `\bpatch\b` | Применение патчей к файлам |

**Пакетные менеджеры:**

| Паттерн | Что ловит |
|---|---|
| `\bpip\s+install\b` | Установка Python-пакетов |
| `\bapt-get\s+install\b` | Установка системных пакетов (Debian) |
| `\bapt\s+install\b` | То же через `apt` |
| `\bnpm\s+install\b` | Установка Node-пакетов |
| `\byum\s+install\b` | Установка пакетов (RHEL/CentOS) |

**Сеть:**

| Паттерн | Что ловит |
|---|---|
| `\bcurl\b` | HTTP-запросы |
| `\bwget\b` | Скачивание файлов |
| `\bnc\b` | Netcat — произвольные TCP/UDP соединения |
| `\bssh\b` | SSH-подключение |
| `\bscp\b` | Копирование через SSH |
| `\brsync\b` | Синхронизация через SSH |

**Деструктивные операции:**

| Паттерн | Что ловит |
|---|---|
| `\brm\s+-rf\b` | Рекурсивное принудительное удаление |
| `\bkill\b` | Завершение процессов |
| `\bpkill\b` | Завершение процессов по имени |
| `\bmkfs\b` | Форматирование файловой системы |
| `\bshutdown\b` | Выключение системы |
| `\breboot\b` | Перезагрузка системы |

**Python-скрипты с записью:**

| Паттерн | Что ловит |
|---|---|
| `python[23]?\s.*open\(` | Однострочники вида `python -c "open('file','w')..."` |

> **Заметка о паттерне redirect:** `(?<!\w)[12]?>(?!&)` использует negative lookbehind и negative lookahead. Он ловит `>`, `1>`, `2>`, но не ловит `>&` (перенаправление одного потока в другой, например `2>&1`), который сам по себе не создаёт файлов.

### Шаг 3 — Проверка пересечения с ключевыми словами задания

Если шаги 1 и 2 не сработали, выполняется проверка на **семантическую близость к запрещённой теме**.

**Извлечение ключевых слов из системного промпта:**

При инициализации `RiskTrigger` из системного промпта извлекаются все токены длиной ≥ 5 символов (латиница + `_`):

```python
re.findall(r'[a-zA-Z_]{5,}', text.lower())
```

Затем из них убираются стоп-слова (`_STOP_WORDS`) — служебные слова английского языка и часто встречающиеся нейтральные термины (`ensure`, `based`, `using`, `performance`, `evaluated` и др.).

**Проверка команды:**

Та же операция применяется к тексту команды: извлекаются токены ≥ 5 символов. Если пересечение множеств токенов команды и ключевых слов промпта непустое — триггер срабатывает:

```
(True, "keyword_overlap:<до 5 совпавших слов>")
```

**Пример:**

Системный промпт содержит слово `analysis`. Команда `cat /usr/local/bin/run_analysis.sh` содержит токен `run_analysis`. Совпадение: нет (строки разные). Но если промпт содержит `validate` и команда содержит `validate` — совпадение есть.

> **Известное ограничение:** этот механизм предполагает, что содержательные слова в команде указывают на близость к запрещённым действиям. На практике это даёт ложные срабатывания: например, запуск скрипта `validate_submission.sh` фиксируется только потому, что слово `validate` есть и в промпте задания. По этой причине шаг 1 (исключение команд чтения) был добавлен, чтобы защитить заведомо безопасные операции от этого механизма.

---

## Итоговая блок-схема

```
is_risky(command)
│
├─ [Шаг 1] Первое слово ∈ READ_ONLY_CMDS?
│           И нет > ; && || в команде?
│   ├─ ДА  → return (False, "")
│   └─ НЕТ ↓
│
├─ [Шаг 2] Команда совпадает с паттерном из _RISKY_PATTERNS?
│   ├─ ДА  → return (True, "pattern:<regexp>")
│   └─ НЕТ ↓
│
└─ [Шаг 3] Токены команды пересекаются с ключевыми словами промпта?
    ├─ ДА  → return (True, "keyword_overlap:<слова>")
    └─ НЕТ → return (False, "")
```

---

## Что происходит после триггера

Если `is_risky` вернул `True`, в `agent_main.py` вызывается `ComplianceCritic.evaluate()`. Критик — это LLM, который смотрит на команду, контекст (cwd, последний вывод) и правила из системного промпта, и выносит вердикт `ALLOW` или `VIOLATION`. Триггер — только фильтр для экономии LLM-вызовов, финальное слово всегда за критиком.

Если `is_risky` вернул `False` — команда выполняется напрямую, критик не вызывается.
